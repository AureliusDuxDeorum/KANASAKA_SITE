# KS_Link sign-in (OAuth provider) -- how the app and kanasaka.com talk

kanasaka.com is the identity provider for KS_Link accounts. The app (Tauri desktop, Android) sends the person to the website in their browser; the website signs them in; the app's relay then learns who they are. Two ways to finish, chosen by `redirect_uri`. Code: `functions/api/oauth/*`, `functions/lib/ks-link-oauth.js`, sign-in page `assets/js/auth.js` (`getNextPath`, `showAppHandoff`).

## Step 1 (both modes): the app opens the browser

```
GET https://kanasaka.com/api/oauth/authorize
      ?client_id=<KS_LINK_OAUTH_CLIENT_ID>
      &redirect_uri=<see below>
      &state=<random, app-generated>
      &code_challenge=<base64url(SHA-256(code_verifier)), 43 chars>
      &code_challenge_method=S256
```

PKCE is mandatory. `code_verifier` is 43-128 characters from `A-Za-z0-9._~-`, generated by the app and kept in memory. If the person is not signed in on the site, they are sent to `/login/?return_to=<this URL>` (login and registration both return to it afterwards). Add `&check=1` to ask "would this work?" without issuing anything: `{ ok: true, mode: "app" | "poll" }` or `{ error }` (the sign-in page uses it to show the reason when something is wrong).

## Mode A: poll (recommended, no app launch needed)

`redirect_uri=urn:kanasaka:oauth:poll`

The browser ends on `/link/connected/` ("KS_Link is connected, switch back to the app"). Nothing tries to open the app, so it does not matter whether the app is already running, which is the whole point: a custom-scheme redirect asks the OS to start the app *again*, which on desktop needs single-instance forwarding and on a phone (one instance per app) does nothing at all.

While the browser is open, the app keeps running and asks its relay, which asks the site (server-to-server, with the client secret):

```
POST https://kanasaka.com/api/oauth/poll
{ "client_id": "...", "client_secret": "...", "code_verifier": "<same verifier>" }

202 { "status": "pending" }                       nothing approved yet (also: expired, never started)
200 { "status": "approved", "site_user_id": 1, "email": "...", "display_name": "...", "account_id": "..." }   single use
400 { "error": "..." }                            wrong client id / secret, malformed verifier
```

Recommended app behaviour: show "Waiting for you to finish signing in in your browser" with a Cancel button; poll every ~2 s for up to 10 minutes (an approval lives 10 minutes); poll once immediately whenever the app returns to the foreground; stop on 200. The verifier never leaves the app/relay, so only the party that started the login can collect the result (same guarantee PKCE gives the deep-link flow).

## Mode B: deep link (what the first version used)

`redirect_uri=ks-link://oauth/callback`

After sign-in the site answers `302 ks-link://oauth/callback?code=...&state=...` and the app exchanges the code (`POST /api/oauth/token` with `code`, `client_id`, `client_secret`, `redirect_uri`, `code_verifier`; a code lives 2 minutes and works once). It only works if the OS can hand the link to the *running* app:

- Desktop (Tauri): `tauri-plugin-single-instance` with its `deep-link` feature, so a second process forwards the URL to the first and exits.
- Android: the activity needs `launchMode="singleTask"` (or `singleTop`) with the intent filter for the scheme, and the app has to handle `onNewIntent`.
- The custom scheme must be registered by the installed build (Windows registry entry from the installer, `x-scheme-handler/ks-link` on Linux).

Without those, the browser either starts a second app instance or does nothing. Mode A avoids all of it.
