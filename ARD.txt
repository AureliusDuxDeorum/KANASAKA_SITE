1. PURPOSE
----------
Static marketing/site shell with gated downloads, contact details, and email-based
account auth. Backend is Cloudflare Pages Functions + D1. No separate VPS.


2. RUNTIME STACK
----------------
Hosting       Cloudflare Pages (branch: main → production)
Functions     Cloudflare Pages Functions under /functions
Database      Cloudflare D1 — kanasaka-auth (id: b76e77d3-4056-4ba2-8356-c69fb65a13d9)

DNS/TLS       Cloudflare
Rate limiting Cloudflare WAF (see docs/CLOUDFLARE_WAF.md); app-level limits removed

4. AUTH DESIGN
--------------
Login/register UI: stepped modal, not dedicated pages
  Login and Register are no longer single-page forms -- clicking the header's
  "Log In"/"Register" opens a centered modal OVER the current page (backdrop
  blur on #site-header/main/#site-footer, no navigation), built entirely by
  JS: assets/js/auth.js's openAuthModal(mode) ("login"|"register"), exposed as
  window.KanasakaAuth.openAuthModal. /login/ and /register/ still exist as
  direct-link targets (bookmarks, ?next=) but now render as a near-empty
  .auth-page shell that auto-opens the same modal on load via
  initProtectedPages(); closing the modal there navigates home since there's
  no prior page to reveal, whereas closing it when opened from any other page
  just removes the overlay in place.
  Login steps: [chooser (skipped if no remembered accounts)] -> email ->
  password (+ "stay logged in") -> verification (2FA, only if required).
  Register steps: accountId (optional, replaces the chooser slot) -> email ->
  password (+ ToS) -> verification (email code) -- verification now happens
  INLINE in the same modal instead of redirecting to /verify/; that page still
  works standalone as a fallback (e.g. if someone closes the modal mid-flow
  and comes back later).
  "Remembered accounts" chooser: client-side only, no server concept of
  "devices". On a successful login/registration where "stay logged in" is
  checked, {email, displayLabel, initials} is saved to localStorage
  (kanasaka:rememberedAccounts, max 5, most-recent-first). The login modal's
  first step shows these as clickable tiles (password still required after
  picking one -- only the email is remembered, never anything that bypasses
  auth) with a per-tile remove (x) button; "Log in with new account" or an
  empty list goes straight to the email step.
  Both flows share one <form> per set of data-entry steps (all fields always
  in the DOM, only one step's div visible at a time) so login()/register()
  (unchanged) can still read fields via form.querySelector('[name=...]')
  regardless of which step is showing, and so browser password-manager
  save-prompts still see email+password together. Enter-key on a non-final
  step is intercepted (bindEnterAdvance) to click that step's own button
  instead of letting the browser hunt for the form's one submit button.
  The old single-page forms/JS (bindEmailPasswordForm, the static
  login-form/register-form/login-2fa-form markup) were removed entirely,
  not kept as a fallback.
  UX polish: submit buttons show a KS-mark spinner (setButtonLoading,
  .ks-spinner in style.css -- the header logo's 4 bars spinning in 90deg
  increments around a counter-rotated, upright "KS") instead of just
  disabling silently. Each numbered step shows "Step N of M" in its eyebrow
  (chooser/verify are unnumbered by design). Password fields get a Show/Hide
  toggle (addPasswordToggle). The modal traps Tab focus and supports Escape
  (modalKeydownHandler); remembered-account chooser tiles are real
  tab-stops (role="button", Enter/Space to select).

Password policy (register, reset, change password)
  Min 15 chars, max 128
  Requires uppercase, lowercase, digit, special character
  Spaces allowed (passphrases OK); no more than 2 identical characters in a row
  Blocklist of common passwords (incl. kanasaka, ksunify)
  Must not contain email local-part (before @)
  Login does NOT re-apply policy (existing shorter passwords still work until changed)
  Server: functions/lib/password-policy.js
  Client: assets/js/password-policy.js (keep in sync)

Registration
  POST /api/auth/register
  Email + password + accountId (unique, permanent) + ToS acceptance.
  Password hashed Argon2id.
  Creates user (email_verified=0), email verify token, sends Resend email.
  Anti-enumeration: existing verified email → generic success; unverified → resend.

Account ID & roles
  account_id: 3–32 chars, lowercase [a-z0-9_-], unique, immutable after set.
  role: user | beta | admin (default user). Assign via D1, or the account-role
  endpoint below, or the in-app Developer panel.
  GET /api/account/id-available?accountId=example — availability check (public)

Admin / developer access (dev_ks)
  functions/lib/roles.js isAdminUser(user) = role==="admin" OR the account_id
  is "dev_ks" (isKsStocksDeveloperAccount from ks-stocks-access.js, the same
  constant that already grants dev_ks permanent KS Stocks + downloads access —
  its own comment documents dev_ks as "permanent developer admin ... all gated
  features"; this extends that same grant to the admin-panel checks below).
  security.js requireAdminAccess(request, env) accepts EITHER the existing
  Authorization: Bearer ADMIN_SECRET header (unchanged, for curl/scripts) OR
  an authenticated session belonging to an isAdminUser account — lets the
  in-app panel call these endpoints with the user's own cookie instead of
  shipping ADMIN_SECRET to the browser. requireAdmin() (secret-only) still
  exists unchanged for functions/api/auth/email-status.js.
  POST /api/admin/account-role — session-or-secret gated (now also
  requireSameOrigin, added when the session path was introduced).
  Body: { "accountId": "example", "role": "admin" }
  GET  /api/admin/lookup?q=<email-or-accountId> — session-or-secret gated,
  returns id/email/accountId/role/emailVerified/twoFactorEnabled/hasPhone/
  createdAt for one account (never the password hash).
  GET  /api/admin/events?limit=N (default 25, max 100) — session-or-secret
  gated, tails auth_events across ALL users (ip/email in meta) for
  diagnostics; there's no other site than dev_ks/admin able to see this.
  UI: Account Settings → "Developer" nav item, hidden unless
  isDev = profile.accountId === "dev_ks" || profile.role === "admin"
  (initDeveloperSettings in auth.js). Shows own session info, the lookup +
  role-change tools above, and a refreshable recent-events tail. Guards
  against a non-admin reaching the panel shell via ?section=developer by
  re-routing back to "personal" once the real profile-based check runs
  (initSettingsNavigation's URL-param handling runs earlier and doesn't
  know the account's role yet).
  NOTE (2026-09-15): dev_ks's role column was still "user" as of this
  writing — isAdminUser's account-id fallback makes it admin-equivalent
  regardless, but the role column itself needs a manual update since D1
  writes aren't run by the agent:
    npx wrangler d1 execute kanasaka-auth --remote --command "UPDATE users SET role = 'admin' WHERE account_id = 'dev_ks';"

  Hardening (2026-09-15, researched against OWASP/NIST privileged-account
  guidance — see change log for sources):
  - 2FA required for the session path: requireAdminAccess additionally
    checks user.totp_enabled and refuses (403, with a message pointing at
    Account Settings) if 2FA isn't on. Bearer-secret access is exempt — it's
    a separate, already-strong trust channel (a long random secret that
    never touches a browser), not a password-equivalent.
  - Step-up re-authentication on the destructive action: account-role.js
    requires body.currentPassword (verified against the ACTING admin's own
    password_hash) whenever called via session, on top of the existing
    session/2FA check — a stolen cookie or unattended device alone can't
    change anyone's role. Not required for bearer-secret calls (no session
    to hijack there).
  - Rate limiting: throttleAdminAction (security.js, reuses the
    tooManyRecentFailures auth_events pattern) caps lookups at 30/10min,
    events views at 60/10min, and role changes at 10/10min, keyed by actor
    (admin's email, or the literal string "secret" for bearer access) — even
    a legitimate-but-compromised admin session can't be used to enumerate
    every account or spam role changes without limit.
  - Full audit trail: lookup.js and events.js previously logged nothing;
    they now call logAuthEvent (admin_lookup, admin_events_viewed) with the
    actor and query/limit, matching the audit trail account-role.js already
    had (admin_role_updated, now also recording previousRole and
    targetEmail, plus a new admin_role_update_failed entry on a bad step-up
    password). All of this shows up in the Developer panel's own event tail.
  - Alerting: sendRoleChangedEmail (email.js) notifies the TARGET account
    (not the acting admin) whenever their role actually changes, with the
    same approxLocation() used by login notifications — if an attacker ever
    got in and escalated some account's privilege, that account's owner
    finds out immediately, not from an audit log nobody's watching.

  Round 2 (2026-09-15, same day — "go more aggressive, crypto-exchange
  style"), functions/lib/pending-changes.js and functions/lib/security-phrase.js:
  - Vault-style time-locked role changes (Coinbase Vault / Kraken Global
    Settings Lock): account-role.js no longer applies a role change
    immediately. It inserts a pending_role_changes row
    (ROLE_CHANGE_DELAY_MINUTES = 30) and emails a cancel link to BOTH the
    target account and the requesting admin. GET /api/admin/cancel-role-change
    ?token=... (no auth required — the token itself is the credential, same
    "magic link" trust model as email verification/reset links) deletes the
    pending row. There's no Cron Trigger here, so "the delay elapsed" is
    checked lazily: resolveSession() (auth.js) applies any due change for
    the CURRENT session's own account on its next authenticated request, and
    GET /api/admin/lookup does the same for whichever account an admin is
    looking at — both via applyDuePendingRoleChanges(). Fails soft to
    pre-hardening immediate-apply if migration 016 hasn't run yet
    (pendingTableExists() try/catches the SELECT). UI: the Developer panel's
    lookup result shows a "Pending change" line when one exists; /admin/
    cancel-role-change/ is the plain-language landing page the emailed link
    opens.
  - Anti-phishing security phrase (Coinbase/Binance pattern): any user can
    set a short phrase (Account Settings → Account Management → Security
    Phrase, step-up password required to change it — functions/api/account/
    security-phrase.js) that gets stamped at the top of their login-
    notification, role-changed, and pending-role-change emails
    (securityPhraseBanner() in email.js). A phishing email impersonating
    KANASAKA won't know the phrase, making it immediately identifiable as
    fake. Column is nullable/optional; emails just render without the
    banner if unset or if migration 016 hasn't run.
  - Escalating lockout (Coinbase-style temporary freeze): 3 wrong step-up
    passwords within 15 minutes (ADMIN_LOCKOUT_FAILURE_THRESHOLD /
    ADMIN_LOCKOUT_WINDOW_MINUTES, security.js) locks out ALL admin
    endpoints for that actor for the rest of the window — checked inside
    requireAdminAccess itself, so it's not just the one action being
    reattempted that's blocked. Sends sendAdminLockoutEmail once per
    lockout window (throttled the same way login failure notifications
    are), not once per blocked request.
  - Deliberately NOT built: WebAuthn/hardware-key MFA (research recommends
    phishing-resistant MFA for admins over TOTP/email codes), a
    last-admin-lockout guard (moot here since dev_ks's account-ID fallback
    means true zero-admin lockout isn't reachable through this UI), and a
    real Cron-triggered apply for pending changes (Cloudflare Pages
    Functions don't run scheduled handlers the way plain Workers do; lazy
    apply-on-next-touch was chosen instead of standing up separate Worker
    infrastructure for one feature) — noted as known gaps/trade-offs rather
    than scope-crept into this change.

Email verification
  6-digit numeric code, not a link. POST /api/auth/register and
  POST /api/auth/resend-verification both call createVerificationCode() (auth.js),
  which generates the code (tokens.js generateNumericCode) and stores it via the
  existing generic createEmailToken()/consumeEmailToken() hash-match machinery
  (type='verify', 15 min expiry — VERIFY_CODE_MINUTES). No schema change needed
  for this part; email_tokens is already a generic hashed-value table.
  POST /api/auth/verify — body { email, code }. Also re-checks the token's
  stored email against the submitted email (defense in depth) and applies a
  best-effort brute-force throttle: >=8 verify_failed auth_events for that email
  in the last 15 min → 429. Throttle read failures fail open (never blocks a
  legitimate attempt).
  Known limitation: two different users could theoretically collide on the same
  6-digit code within its validity window, causing a UNIQUE constraint failure
  on the second INSERT (surfaces as a registration/resend error) — accepted as
  low-probability at current scale, not fully mitigated.
  UI: /verify/ is a real form (email + code inputs, resend button), not an
  auto-submitting link handler. Register redirects to /verify/?email=... on
  success instead of showing an inline "check your email" message.

Login / session ("stay logged in")
  POST /api/auth/login — body may include remember: boolean (checkbox on the
  login form, default checked). cookie __Host-kanasaka_session (HttpOnly,
  SameSite=Strict). remember=true sets Max-Age for a persistent cookie;
  remember=false omits Max-Age entirely for a true browser-session cookie that
  the browser discards on close. The chosen value is stored on the session row
  (sessions.remember, migration 015) so it survives automatic session rotation
  (SESSION_ROTATE_HOURS); without that column, rotateSession() falls back to
  always remembering (safe default, not a security gap) until 015 is applied.
  If totp_enabled: returns { twoFactorRequired, challenge, expiresIn } (no cookie yet);
  remember is threaded through the 2FA challenge too (twofa_challenges.remember,
  also migration 015) so it's honored after the code step completes.
  POST /api/auth/two-factor — completes login with TOTP or backup code
  Session token: 32-byte random, only HMAC digest stored in D1 (needs SESSION_SECRET)
  Session rotation: every SESSION_ROTATE_HOURS (default 24h) via resolveSession()
  GET /api/auth/session — current user payload
  Note: /api/account/password's post-password-change session refresh does not
  thread the prior remember choice through (defaults to remember=true) — a
  deliberate scope cut since that's an already-authenticated settings action,
  not a login.

Login notifications
  Every login.js branch that resolves a real user account emails that
  account (notifyLogin in functions/lib/security.js, which wraps
  sendLoginNotificationEmail from email.js) with the outcome — wrong
  password, unverified account, 2FA requested/misconfigured, or full
  success — plus an approximate location and timestamp. The email never
  contains the raw IP; approxLocation() (security.js) reads city/region/
  country off Cloudflare's request.cf (already attached to every request
  at the edge, no external geo-IP lookup) and formats e.g. "Frankfurt,
  Hesse, DE". The raw IP is still logged internally in auth_events for
  the site's own security monitoring, just never emailed to the user.
  functions/api/auth/two-factor.js does the same for the code-entry step
  itself (correct or incorrect code).
  Skipped only when no real account was identified (unknown email / invalid
  input) — there's no valid destination to notify. When 2FA method is email,
  the "requested" notification at the password step is skipped since the
  code email itself already serves that purpose (SMS still gets its own,
  since it's a different channel). Best-effort: a Resend failure here is
  caught and logged, never blocks the login/2FA response itself.
  Throttled: successful sign-ins always notify (rare, most important to
  never miss), but failure/blocked outcomes are capped at one email per
  account per LOGIN_NOTIFICATION_THROTTLE_MINUTES (10 min) — reuses
  tooManyRecentFailures() against a "login_notification_sent" auth_events
  marker, same no-new-schema pattern as the verify/reset-password
  throttles. A password-guessing burst against a known email produces one
  alert, not one email per attempt.

Two-factor authentication (email code)
  Optional per account. `users.totp_enabled` is the generic "2FA on" flag;
  method is inferred, not a separate column: phone_e164 set → sms, else → email.
  UI (Account Settings → Account Management → Two-Factor Authentication) only
  offers Email — it's the one method that works without paid Twilio setup.
  POST /api/account/two-factor/email-setup — send a 6-digit code to account email
  POST /api/account/two-factor/email-enable — confirm code, enables 2FA
  POST /api/account/two-factor/disable — code only (no password re-entry;
    the emailed code is the only factor required to turn it off); branches
    on phone_e164 to call disableSms2fa or disableEmail2fa (two-factor.js)
  POST /api/account/two-factor/send-code {purpose:"disable"} — resend disable code
  Login: login.js branches the same way; if method is sms and Twilio isn't
    configured, login is now refused with a 503 rather than silently skipping
    the 2FA step (a real gap in the code found and fixed while building this —
    previously `user.totp_enabled && smsConfigured(env)` would bypass 2FA
    entirely whenever SMS wasn't configured).
  Login UI: the auth modal's verify step (see "Login/register UI" above)
    shows the code-entry form when the server returns twoFactorRequired; no
    resend button on this step (re-submitting the login form issues a fresh
    challenge + code instead).
  functions/api/account/two-factor/setup.js, enable.js — legacy SMS-only setup
    endpoints (phone number entry). Backend only, no frontend ever built, and
    smsConfigured(env) requires TWILIO_ACCOUNT_SID/AUTH_TOKEN/FROM_NUMBER which
    aren't set — effectively dead code, left in place, not wired to any UI.
  functions/lib/totp.js (RFC 6238) is unused/dead — no code path issues real
    TOTP secrets despite the naming.

Backup codes (2026-09-15 — closes the "no 2FA recovery path" gap)
  twofa_backup_codes was schema-only (migration 008) until now — nothing
  ever wrote to it. generateBackupCodes(env, userId) (two-factor.js) issues
  BACKUP_CODE_COUNT=8 codes (format XXXXX-XXXXX, 32-char alphabet excluding
  0/O/1/I to avoid misreads), hashed with the same hashSecret() as
  everything else, replacing any previous set. Called from enableEmail2fa
  (returned once, alongside emailMasked, in the email-enable response) and
  from POST /api/account/two-factor/regenerate-backup-codes (session +
  current-password required, same step-up pattern as everything else in
  Account Settings).
  verifyTwoFactorLogin tries the normal emailed OTP first, then falls back
  to verifyBackupCode() (marks the code used_at, one-time) -- a backup code
  is NOT 6 digits so it never matches the OTP regex, so there's no ambiguity
  between the two checks.
  UI: Account Settings → Two-Factor Authentication shows the codes once
  right after enabling (dismissible, never shown again) and a live "N
  backup codes remaining" count (profilePayload.backupCodesRemaining) plus
  a "Regenerate Backup Codes" action. The login modal's verification step
  has a "Use a backup code instead" toggle that swaps the 6 OTP boxes for a
  single plain-text field (auth.js renderAuthModalLogin) -- backup codes
  don't fit the 6-digit-box shape.

Password reset (6-digit email code, same pattern as email verification)
  POST /api/auth/forgot-password → generic success + createPasswordResetCode()
    (type='reset' in email_tokens, RESET_CODE_MINUTES=15), emails the code
  POST /api/auth/reset-password — body {email, code, password}; re-checks the
    token's stored email against the submitted email, brute-force throttle via
    security.js tooManyRecentFailures() (shared with /api/auth/verify), then
    updates password and invalidates all sessions
  UI: /forgot-password/ redirects to /reset-password/?email=... on submit;
    /reset-password/ has email + code + new-password fields and a resend link

Account
  /api/account/profile, /password, /avatar, /delete
  /api/account/avatar upload validates the actual file bytes (magic-number
  signature check, isValidImageSignature in profile.js), not just the
  client-supplied Content-Type -- a renamed/relabeled file no longer gets
  stored and served back just because the upload's MIME type header claimed
  to be an image. Client-type + magic-byte type must both match one of
  AVATAR_MIME_TYPES.

Security
  requireSameOrigin() on mutating auth routes
  logAuthEvent() → auth_events table (best-effort)
  Legacy PBKDF2 hashes still verify; upgraded to Argon2 on login
  App-level rate limiting on auth endpoints is minimal (the throttles in
  security.js are aimed at low-entropy codes and admin actions specifically,
  not general request-flood protection) -- primary abuse control is meant
  to be Cloudflare WAF/Rate Limiting rules per docs/CLOUDFLARE_WAF.md, and
  as of 2026-09-15 those are STILL UNVERIFIED (scripts/check-waf-rules.mjs
  fails with "Invalid access token" -- the wrangler OAuth token in this
  environment only has account/user/workers scopes, no Zone/WAF permission,
  so neither reading nor applying these rules is possible via this token).
  Apply the 6 rules in docs/CLOUDFLARE_WAF.md manually from the Cloudflare
  dashboard (Security → WAF → Custom rules / Rate limiting rules), or issue
  a Zone-scoped API token (Zone > Firewall Services > Edit, or the newer
  Rulesets Edit permission) if you want this automated later.


5. D1 SCHEMA (CURRENT — post migration 008)
-------------------------------------------
users
  id INTEGER PK, email TEXT UNIQUE NOCASE, password_hash TEXT,
  email_verified INTEGER, created_at TEXT, display_name TEXT,
  account_id TEXT UNIQUE NOCASE, role TEXT DEFAULT 'user',
  tos_accepted_at TEXT, tos_version TEXT,
  totp_secret TEXT, totp_pending_secret TEXT,
  totp_enabled INTEGER DEFAULT 0, totp_enabled_at TEXT,
  phone_e164 TEXT, phone_pending_e164 TEXT,
  security_phrase TEXT (migration 016, not yet applied remotely)

pending_role_changes (migration 016, not yet applied remotely)
  id INTEGER PK, user_id INTEGER FK, previous_role TEXT, new_role TEXT,
  requested_by TEXT (admin's email, or "secret"), cancel_token_hash TEXT UNIQUE,
  effective_at TEXT, created_at TEXT

sessions
  id INTEGER PK, token_hash TEXT UNIQUE, user_id INTEGER FK,
  expires_at TEXT, created_at TEXT, last_rotated_at TEXT,
  remember INTEGER (migration 015, not yet applied remotely as of this writing)

email_tokens
  id INTEGER PK, token_hash TEXT UNIQUE, user_id INTEGER FK,
  type TEXT ('verify'|'reset'), expires_at TEXT, created_at TEXT

user_avatars
  user_id INTEGER PK FK, mime_type TEXT, data BLOB, updated_at TEXT

auth_events
  id INTEGER PK, event_type TEXT, meta TEXT JSON, created_at TEXT

twofa_backup_codes
  id INTEGER PK, user_id INTEGER FK, code_hash TEXT, used_at TEXT, created_at TEXT

twofa_challenges
  id INTEGER PK, challenge_hash TEXT UNIQUE, user_id INTEGER FK,
  expires_at TEXT, created_at TEXT,
  remember INTEGER (migration 015, not yet applied remotely as of this writing)

rate_limits
  key TEXT PK, count INTEGER, window_start TEXT
  (legacy table; app no longer writes — WAF handles rate limits)

schema.js detects token_hash vs legacy id-based token tables at runtime.
