1. PURPOSE
----------
Static marketing/site shell with gated downloads, contact details, and email-based
account auth. Backend is Cloudflare Pages Functions + D1. No separate VPS.

----------------

4. AUTH DESIGN
--------------
Password policy (register, reset, change password)
  Min 15 chars, max 128
  Requires uppercase, lowercase, digit, special character
  Spaces allowed (passphrases OK); no more than 2 identical characters in a row
  Blocklist of common passwords (incl. kanasaka, ksunify)
  Must not contain email local-part (before @)
  Login does NOT re-apply policy (existing shorter passwords still work until changed)
  Server: functions/lib/password-policy.js
  Client: assets/js/password-policy.js (keep in sync)

Registration
  POST /api/auth/register
  Email + password + accountId (unique, permanent) + ToS acceptance.
  Password hashed Argon2id.
  Creates user (email_verified=0), email verify token, sends Resend email.
  Anti-enumeration: existing verified email → generic success; unverified → resend.

Account ID & roles
  account_id: 3–32 chars, lowercase [a-z0-9_-], unique, immutable after set.
  role: user | beta | admin (default user). Assign via D1 or:
  POST /api/admin/account-role  Authorization: Bearer ADMIN_SECRET
  Body: { "accountId": "example", "role": "admin" }
  GET /api/account/id-available?accountId=example — availability check (public)

Email verification
  6-digit numeric code, not a link. POST /api/auth/register and
  POST /api/auth/resend-verification both call createVerificationCode() (auth.js),
  which generates the code (tokens.js generateNumericCode) and stores it via the
  existing generic createEmailToken()/consumeEmailToken() hash-match machinery
  (type='verify', 15 min expiry — VERIFY_CODE_MINUTES). No schema change needed
  for this part; email_tokens is already a generic hashed-value table.
  POST /api/auth/verify — body { email, code }. Also re-checks the token's
  stored email against the submitted email (defense in depth) and applies a
  best-effort brute-force throttle: >=8 verify_failed auth_events for that email
  in the last 15 min → 429. Throttle read failures fail open (never blocks a
  legitimate attempt).
  Known limitation: two different users could theoretically collide on the same
  6-digit code within its validity window, causing a UNIQUE constraint failure
  on the second INSERT (surfaces as a registration/resend error) — accepted as
  low-probability at current scale, not fully mitigated.
  UI: /verify/ is a real form (email + code inputs, resend button), not an
  auto-submitting link handler. Register redirects to /verify/?email=... on
  success instead of showing an inline "check your email" message.

Login / session ("stay logged in")
  POST /api/auth/login — body may include remember: boolean (checkbox on the
  login form, default checked). cookie __Host-kanasaka_session (HttpOnly,
  SameSite=Strict). remember=true sets Max-Age for a persistent cookie;
  remember=false omits Max-Age entirely for a true browser-session cookie that
  the browser discards on close. The chosen value is stored on the session row
  (sessions.remember, migration 015) so it survives automatic session rotation
  (SESSION_ROTATE_HOURS); without that column, rotateSession() falls back to
  always remembering (safe default, not a security gap) until 015 is applied.
  If totp_enabled: returns { twoFactorRequired, challenge, expiresIn } (no cookie yet);
  remember is threaded through the 2FA challenge too (twofa_challenges.remember,
  also migration 015) so it's honored after the code step completes.
  POST /api/auth/two-factor — completes login with TOTP or backup code
  Session token: 32-byte random, only HMAC digest stored in D1 (needs SESSION_SECRET)
  Session rotation: every SESSION_ROTATE_HOURS (default 24h) via resolveSession()
  GET /api/auth/session — current user payload
  Note: /api/account/password's post-password-change session refresh does not
  thread the prior remember choice through (defaults to remember=true) — a
  deliberate scope cut since that's an already-authenticated settings action,
  not a login.

Login notifications
  Every login.js branch that resolves a real user account emails that
  account (notifyLogin in functions/lib/security.js, which wraps
  sendLoginNotificationEmail from email.js) with the outcome — wrong
  password, unverified account, 2FA requested/misconfigured, or full
  success — plus an approximate location and timestamp. The email never
  contains the raw IP; approxLocation() (security.js) reads city/region/
  country off Cloudflare's request.cf (already attached to every request
  at the edge, no external geo-IP lookup) and formats e.g. "Frankfurt,
  Hesse, DE". The raw IP is still logged internally in auth_events for
  the site's own security monitoring, just never emailed to the user.
  functions/api/auth/two-factor.js does the same for the code-entry step
  itself (correct or incorrect code).
  Skipped only when no real account was identified (unknown email / invalid
  input) — there's no valid destination to notify. When 2FA method is email,
  the "requested" notification at the password step is skipped since the
  code email itself already serves that purpose (SMS still gets its own,
  since it's a different channel). Best-effort: a Resend failure here is
  caught and logged, never blocks the login/2FA response itself.
  Throttled: successful sign-ins always notify (rare, most important to
  never miss), but failure/blocked outcomes are capped at one email per
  account per LOGIN_NOTIFICATION_THROTTLE_MINUTES (10 min) — reuses
  tooManyRecentFailures() against a "login_notification_sent" auth_events
  marker, same no-new-schema pattern as the verify/reset-password
  throttles. A password-guessing burst against a known email produces one
  alert, not one email per attempt.

Two-factor authentication (email code)
  Optional per account. `users.totp_enabled` is the generic "2FA on" flag;
  method is inferred, not a separate column: phone_e164 set → sms, else → email.
  UI (Account Settings → Account Management → Two-Factor Authentication) only
  offers Email — it's the one method that works without paid Twilio setup.
  POST /api/account/two-factor/email-setup — send a 6-digit code to account email
  POST /api/account/two-factor/email-enable — confirm code, enables 2FA
  POST /api/account/two-factor/disable — code only (no password re-entry;
    the emailed code is the only factor required to turn it off); branches
    on phone_e164 to call disableSms2fa or disableEmail2fa (two-factor.js)
  POST /api/account/two-factor/send-code {purpose:"disable"} — resend disable code
  Login: login.js branches the same way; if method is sms and Twilio isn't
    configured, login is now refused with a 503 rather than silently skipping
    the 2FA step (a real gap in the code found and fixed while building this —
    previously `user.totp_enabled && smsConfigured(env)` would bypass 2FA
    entirely whenever SMS wasn't configured).
  Login UI: /login/ shows a code-entry step (#login-2fa-form) when the server
    returns twoFactorRequired; no resend button on this step (re-submitting the
    login form issues a fresh challenge + code instead).
  functions/api/account/two-factor/setup.js, enable.js — legacy SMS-only setup
    endpoints (phone number entry). Backend only, no frontend ever built, and
    smsConfigured(env) requires TWILIO_ACCOUNT_SID/AUTH_TOKEN/FROM_NUMBER which
    aren't set — effectively dead code, left in place, not wired to any UI.
  functions/lib/totp.js (RFC 6238) and twofa_backup_codes are unused/dead —
    no code path issues real TOTP secrets or backup codes despite the naming.

Password reset (6-digit email code, same pattern as email verification)
  POST /api/auth/forgot-password → generic success + createPasswordResetCode()
    (type='reset' in email_tokens, RESET_CODE_MINUTES=15), emails the code
  POST /api/auth/reset-password — body {email, code, password}; re-checks the
    token's stored email against the submitted email, brute-force throttle via
    security.js tooManyRecentFailures() (shared with /api/auth/verify), then
    updates password and invalidates all sessions
  UI: /forgot-password/ redirects to /reset-password/?email=... on submit;
    /reset-password/ has email + code + new-password fields and a resend link

Account
  /api/account/profile, /password, /avatar, /delete

Security
  requireSameOrigin() on mutating auth routes
  logAuthEvent() → auth_events table (best-effort)
  Legacy PBKDF2 hashes still verify; upgraded to Argon2 on login


5. D1 SCHEMA (CURRENT — post migration 008)
-------------------------------------------
users
  id INTEGER PK, email TEXT UNIQUE NOCASE, password_hash TEXT,
  email_verified INTEGER, created_at TEXT, display_name TEXT,
  account_id TEXT UNIQUE NOCASE, role TEXT DEFAULT 'user',
  tos_accepted_at TEXT, tos_version TEXT,
  totp_secret TEXT, totp_pending_secret TEXT,
  totp_enabled INTEGER DEFAULT 0, totp_enabled_at TEXT,
  phone_e164 TEXT, phone_pending_e164 TEXT

sessions
  id INTEGER PK, token_hash TEXT UNIQUE, user_id INTEGER FK,
  expires_at TEXT, created_at TEXT, last_rotated_at TEXT,
  remember INTEGER (migration 015, not yet applied remotely as of this writing)

email_tokens
  id INTEGER PK, token_hash TEXT UNIQUE, user_id INTEGER FK,
  type TEXT ('verify'|'reset'), expires_at TEXT, created_at TEXT

user_avatars
  user_id INTEGER PK FK, mime_type TEXT, data BLOB, updated_at TEXT

auth_events
  id INTEGER PK, event_type TEXT, meta TEXT JSON, created_at TEXT

twofa_backup_codes
  id INTEGER PK, user_id INTEGER FK, code_hash TEXT, used_at TEXT, created_at TEXT

twofa_challenges
  id INTEGER PK, challenge_hash TEXT UNIQUE, user_id INTEGER FK,
  expires_at TEXT, created_at TEXT,
  remember INTEGER (migration 015, not yet applied remotely as of this writing)

rate_limits
  key TEXT PK, count INTEGER, window_start TEXT
  (legacy table; app no longer writes — WAF handles rate limits)

schema.js detects token_hash vs legacy id-based token tables at runtime.

9. DOWNLOADS
------------
Gated behind login at /downloads/
GET /api/download/{platform} — auth check → 302 to signed /api/download/file?token=...
GET /api/download/file — validates HMAC token (5 min TTL), streams object from R2
Platforms: windows (.exe), linux (.deb), macos (.dmg)
R2 bucket: kanasaka-installers (enable R2 in dashboard, bind INSTALLERS in Pages)
Upload: node scripts/upload-installers-r2.mjs (see docs/R2_INSTALLERS.md)
Legacy GitHub URLs removed from download flow (DOWNLOAD_URLS may remain in auth.js)
KS Unify desktop app (separate repo) uses cookie-jar auth client — no localStorage tokens.
